## P0 — Blocking / structural (nothing above this works right until these land)

- [x] **Fixed a live signup privilege-escalation vulnerability (2026-08-15).** `handle_new_auth_user()` cast `raw_user_meta_data->>'role'` directly to `user_role` with no allowlist — since that metadata is fully client-controlled, any caller of the public signup API could self-assign `admin`/`pso_supervisor`/`pso_staff` (confirmed live: signed up a throwaway account with `role: 'admin'` in the metadata and it really landed as `role='admin'` in `public.users`, before the fix). Found while debugging the admin app's Driver/Passenger Management wiring. Fixed by restricting signup metadata to only ever grant `'driver'` (when requested) or `'passenger'` (default) — privileged roles are unreachable via self-service signup now, full stop. Zero client-side changes needed; re-verified live afterward that `role: 'admin'` now correctly lands as `passenger`, and that legitimate driver self-signup (`role: 'driver'`) still works and still provisions `driver_profiles`.
- [x] **Fixed Suspend/Block having no actual effect (2026-08-15).** PSO suspending/blocking a user via the admin app wrote `users.status` correctly, but nothing anywhere — not RLS, not either app — ever read that column, so a suspended driver could keep accepting rides and a blocked passenger could keep booking, completely unaffected. New `is_account_active()` helper (`status in ('active','flagged')`) now gates: `ride_requests` read/accept for a driver's *new* pending requests, `ride_requests` insert for a passenger, and `driver_profiles.is_available` going true — deliberately *not* gating a ride_request already tied to the driver's own active trip, so a suspension landing mid-ride doesn't strand the passenger. Driver app also gained an `account-suspended` screen (mirrors the existing verification-pending pattern) that the root layout now routes to once `users.status` is `suspended`/`deactivated`, unless there's an active trip in progress. All of this was live-verified against the real project: RLS policy behavior via rolled-back transactions (`set local role authenticated` + `set_config('request.jwt.claim.sub', ...)`), and the UI gate via a real Expo-web session — logged in as a throwaway driver, suspended it through the real `perform_account_action` RPC, confirmed the app showed "Your account has been suspended" on reload, then reactivated and confirmed normal access returned. Passenger app doesn't have the equivalent blocked-screen yet — flagged as a follow-up, not done in this pass.
- [x] **Build `match-ride-request` Edge Function** — deployed 2026-08-05 (`supabase/functions/match-ride-request/index.ts`, ACTIVE on the live project). Implements the FR-2.5 two-stage check: cluster-authorization hard filter (mirrors `is_cluster_authorized()`) + seat capacity, then a bearing-tolerance/detour-ratio soft filter once the driver has a known position. `subscribeToPendingRideRequests()` (`packages/services/src/booking/index.ts`) now calls it instead of the old naive full-table select; `useRequestsStore.subscribe()` and the Dashboard toggle were updated to pass `driverId` through. All 66 existing unit tests (49 services + 17 driver) and both composite typechecks (`apps/driver`, `apps/passenger`) still pass.
  - **Soft filter won't activate yet**: it depends on `driver_profiles.current_lat/current_lng`, which nothing writes today — see the P0 item below ("Driver availability toggle...") and the still-stub `packages/services/src/location/index.ts`. Until then the function correctly falls back to the hard-filtered list only (cluster + capacity), which is still a real improvement over the old unfiltered board.
- [x] **Fixed a live bug that made every ride request invisible to every driver, always (2026-08-15).** First real end-to-end live smoke test of `match-ride-request` (a real verified driver, real GPS, real passenger booking) found the "Incoming request" card never appeared. Root cause: `createRideRequest()` (`packages/services/src/booking/index.ts`) never populates `ride_requests.pickup_barangay_id` — there's no barangay-boundary geodata in the schema to resolve it from GPS coordinates (`barangays` has no geometry/centroid columns, confirmed live), so it's always `null`. The Edge Function's hard filter (`isClusterAuthorized`) unconditionally rejected a `null` barangay cluster, so the ordinance cluster check silently rejected 100% of requests, for every driver, since the function was deployed. Fixed by allowing a request with an unresolved barangay cluster through the hard filter (previously: excluded) — deployed as `match-ride-request` v4. This is a deliberate interim relaxation, not a real fix for barangay resolution; the ordinance's cluster restriction becomes enforceable again for a given request only once `pickup_barangay_id` is actually populated (still deferred pending barangay geodata, see `docs/superpowers/specs/2026-08-02-ride-request-insert-design.md`). Re-verified live afterward: created a real ride request, invoked the deployed function directly as a real verified driver, request appeared. All test data cleaned up.
- [x] **Fixed a live 400 on every driver app boot (2026-08-15).** `get_active_trip_for_driver()` — called by `useTripSync`'s `hydrate()` on every app start — threw `42702: column reference "started_at" is ambiguous`, because `RETURNS TABLE(..., started_at timestamptz, ...)` implicitly declares `started_at` as a PL/pgSQL variable, colliding with the `trips.started_at` column referenced unqualified in the function body. The error was silently swallowed by the store's own error handling, so nothing crashed, but trip rehydration after an app restart never worked. Fixed by qualifying the column reference (`select t.id, t.started_at ... from public.trips t`). Re-verified live via a rolled-back transaction authenticated as a real driver — no error, correct empty result.
- [x] **Fixed `signOut()` silently logging out other devices/sessions (2026-08-15).** Found via a real driver's live device logs: the request board threw a raw "Edge Function returned a non-2xx status code" even though the driver's JWT hadn't expired — GoTrue's own logs showed `/user` returning 403 `session_not_found` for that token. Root cause: `signOut()` (`packages/services/src/auth/index.ts`, shared by all three apps) called `auth.signOut()` with no options, which defaults to `scope: 'global'` — revoking *every* session for that user account, not just the one signing out. A sign-out on one device (or a second test session) was silently killing an already-running session elsewhere, which then failed its next Edge Function call with a technical-looking 401. Fixed by passing `{ scope: 'local' }`. Also translated that failure mode into driver-facing copy ("Your session expired. Please log out and log back in.") in `subscribeToPendingRideRequests` (`packages/services/src/booking/index.ts`) instead of surfacing the SDK's raw error string — it reads `error.context` (the actual Edge Function response body), which the SDK's own `.message` never exposes. New/updated tests in `packages/services/tests/{auth,booking}.test.ts`; full `packages/services` (146/146) and `apps/driver` (39/39) suites pass, typecheck clean.
- [x] **Build `paymongo-webhook` Edge Function** *(renamed from `gcash-webhook`)* — deployed 2026-08-07, along with a new `create-gcash-checkout` Edge Function it depends on (the checklist originally scoped just the webhook, but the webhook has nothing to confirm without something creating the PayMongo Checkout Session first — see `docs/superpowers/specs/2026-08-07-paymongo-webhook-design.md`). `create-gcash-checkout` (`verify_jwt: true`) authenticates the passenger, locks the charge to `ride_requests.final_fare`, and is idempotent by `ride_request_id` (reuses an unexpired pending session rather than duplicating). `paymongo-webhook` (`verify_jwt: false`, PayMongo authenticates via its own signature instead) verifies `Paymongo-Signature` (HMAC-SHA256, timing-safe compare) against the raw body before parsing, and is the only place `transactions.status` ever becomes `'paid'` — guarded by `WHERE status = 'pending'` for idempotent replay handling. `amount` is fixed once at checkout-session creation and never touched by the webhook.
  - **Also fixed a real gap found during design**: `final_fare` (documented as "locked at trip completion") was never actually written anywhere — `completeTrip()` in `packages/services/src/booking/index.ts` now copies `estimated_fare` into it, since GCash checkout amount depends on it being non-null.

Signature verification passed against a real PayMongo delivery (200, not 401) — the code doesn't log which of its two header-format branches matched on a successful verification, so it's confirmed *working*, not confirmed *which branch*; add temporary logging on the success path if that distinction ever matters.

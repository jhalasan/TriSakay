Implements the FR-2.5 two-stage check: cluster-authorization hard filter (mirrors `is_cluster_authorized()`) + seat capacity, then a bearing-tolerance/detour-ratio soft filter once the driver has a known position. `subscribeToPendingRideRequests()` (`packages/services/src/booking/index.ts`) now calls it instead of the old naive full-table select; `useRequestsStore.subscribe()` and the Dashboard toggle were updated to pass `driverId` through. All 66 existing unit tests (49 services + 17 driver) and both composite typechecks (`apps/driver`, `apps/passenger`) still pass.
  - **Not yet exercised live**: no end-to-end smoke test was run against the deployed function (would need a seeded verified driver + tricycle + pending request; out of scope for this pass) — verify during the next real QA session.
  - **Soft filter won't activate yet**: it depends on `driver_profiles.current_lat/current_lng`, which nothing writes today — see the P0 item below ("Driver availability toggle...") and the still-stub `packages/services/src/location/index.ts`. Until then the function correctly falls back to the hard-filtered list only (cluster + capacity), which is still a real improvement over the old unfiltered board.
- [x] **Build `paymongo-webhook` Edge Function** *(renamed from `gcash-webhook`)* — deployed 2026-08-07, along with a new `create-gcash-checkout` Edge Function it depends on (the checklist originally scoped just the webhook, but the webhook has nothing to confirm without something creating the PayMongo Checkout Session first — see `docs/superpowers/specs/2026-08-07-paymongo-webhook-design.md`). `create-gcash-checkout` (`verify_jwt: true`) authenticates the passenger, locks the charge to `ride_requests.final_fare`, and is idempotent by `ride_request_id` (reuses an unexpired pending session rather than duplicating). `paymongo-webhook` (`verify_jwt: false`, PayMongo authenticates via its own signature instead) verifies `Paymongo-Signature` (HMAC-SHA256, timing-safe compare) against the raw body before parsing, and is the only place `transactions.status` ever becomes `'paid'` — guarded by `WHERE status = 'pending'` for idempotent replay handling. `amount` is fixed once at checkout-session creation and never touched by the webhook.
  - **Also fixed a real gap found during design**: `final_fare` (documented as "locked at trip completion") was never actually written anywhere — `completeTrip()` in `packages/services/src/booking/index.ts` now copies `estimated_fare` into it, since GCash checkout amount depends on it being non-null.
  - **`payment.tsx` wired for real**: GCash "Pay now" opens PayMongo's hosted checkout in an in-app browser (`expo-web-browser`) and relies solely on a Realtime subscription to `transactions.status` to advance the UI — the browser closing/redirecting is never trusted, per FR-9.2. Includes a 2-minute timeout and retry/cash-fallback UI (FR-9.8).
  - **Verified live end-to-end** (2026-08-07): seeded a real completed `ride_requests`/`trips` pair for a throwaway test passenger account, called `create-gcash-checkout` for real, completed a genuine PayMongo test-mode GCash payment, and confirmed `transactions.status` flipped `pending → paid` via the real webhook delivery (all test data cleaned up after). Signature verification passed against a real PayMongo delivery (200, not 401) — the code doesn't log which of its two header-format branches matched on a successful verification, so it's confirmed *working*, not confirmed *which branch*; add temporary logging on the success path if that distinction ever matters.
  - **A live 500 was hit and fixed mid-testing**: the webhook's reference lookup used `.eq('id', referenceNumber)` against a `uuid` column; a malformed/non-UUID reference caused a raw Postgres error instead of a clean ignore. Added a UUID-shape guard (`isUuid()`) so an unresolvable reference now returns 200 instead of a 500 PayMongo would retry indefinitely.
  - **`payment.failed` handling is still unconfirmed** — no real declined-payment webhook delivery was tested live, so the reference-extraction logic for that event type remains a best-effort guess (see the file's own comment) until it's exercised against a real failed-payment delivery.
  - **A final whole-branch review caught two more real bugs before merge**, both fixed: (1) `transactions` had never been added to Supabase's `supabase_realtime` publication (`alter publication supabase_realtime add table public.transactions;`, applied live and documented in `docs/SCHEMA.MD` §9) — without this the passenger app's Realtime subscription could never actually receive a payment confirmation, even though the DB-level flip worked; (2) a race where a webhook marking a row `'paid'` mid-flight could be silently clobbered back to `'pending'` by a slow `create-gcash-checkout` invocation finishing afterward — fixed with a `.neq('status', 'paid')` guard on that update, redeployed.
  - **Known limitation at the time, since fixed**: at the time this task was verified, `payment.tsx` was only reachable via `trip-in-progress.tsx`'s mock `wait(5-8s)` timer, not real trip completion — so the live app would let a passenger reach "Pay now" before `ride_requests.status` was actually `'completed'`, and the RPC/RLS would reject it. The live end-to-end verification above worked around this by seeding a real completed ride directly. This gap is now closed by the P1 item below ("Passenger: trip tracking after match") — `trip.tsx` now navigates to `payment.tsx` only after a real `ride_requests.status === 'completed'` Realtime event, so the organic user path is unblocked.
- [x] **Driver availability toggle → real `driver_profiles.is_available` write.** Dashboard's toggle now calls a real `updateDriverAvailability()` (`packages/services/src/location/index.ts`) — going online takes a one-time `expo-location` GPS fix in `dashboard.tsx` and writes `is_available`/`current_lat`/`current_lng`; going offline just writes `is_available: false` (the `clear_location_when_offline` trigger nulls the rest server-side, so the client never needs to). The two `enforce_driver_verified_before_available` trigger exceptions (verification not approved / no verified tricycle) are translated into driver-facing copy instead of a raw Postgres error. `logout.tsx` reordered to go offline *before* signing out — the write needs the still-live session. New tests in `packages/services/tests/location.test.ts`.

Fixed across the whole package (`supabase/index.ts`, `supabase/client.ts`, `storage/index.ts`, `discount/index.ts`, and the `database.types` imports in `auth`/`consents`/`driver-profile`), not just the file this task touched.
  - **Not yet exercised on-device**: verified via live-schema inspection (columns/RLS/triggers read directly off the Supabase project via MCP) plus typecheck + unit tests (72 driver+services, all passing) — still needs a real phone test to confirm the GPS-permission path and the trigger's two rejection cases behave as expected end-to-end.
  - **Continuous location tracking is still out of scope** — this is a one-time fix on toggle-on, not a `watchPositionAsync` subscription. Revisit once the soft-filter matching (FR-2.5) needs live position, not just "was online."
